## 2. Bug Fixes Detailed Spec

### 2.1 BUG-01: Credential cards disappear because no snapshot is built after a quota probe (TriggerProbe)

#### Root cause
In `internal/runtime/production_runner.go`, when the request mode is `TriggerProbe` (i.e. clicking "Refresh quota"), the backend collected quota evidence, persisted it to the cache, and then returned early with `return nil`.  
**Effect**: the subsequent `PlanFreshOnly` calculation and `r.setDualSnapshot(dualSnap)` were skipped entirely, and `latestResult` was overwritten with an empty object. When the frontend called `refreshDashboard()` after the probe and fetched `/snapshot/latest`, it got an empty list and every card disappeared.

#### Fix
1. Reorder the `production_runner.go` pipeline: after `store.SaveAtomic`, always run the two-group Plan calculation and `r.setDualSnapshot(dualSnap)`, regardless of Trigger mode.
2. For `TriggerProbe`, build a complete `apply.Result` containing `primarySnapshot` and persist it via `store.SetRuntimeSnapshot`.
3. Ensure that when the frontend re-fetches the snapshot after a probe, the credential cards always show the latest probed quota in full.

### 2.2 BUG-02: Snapshot not synced after priority Reset, and Apply wrongly blocked

#### Root cause
1. On `POST /reset` (reset priorities), the backend cleared the `priority` field in the CPA host but did not update the in-memory `latestDualSnapshot`. After a refresh the frontend still received the old `target.priority` (showing 100), making the reset look like it had no effect.
2. The frontend `triggerRun("apply")` had a static check `if (changes.length === 0)`. Because no diff was generated after the reset, the frontend showed a Toast saying *"Credential state and priorities are already optimal; nothing to write back"*, forcing the user to run a Dry-Run first before Apply would work.

#### Fix
1. Refactor `Runtime.ResetAllPriorities`:
   - After clearing host priorities, mark every in-memory credential as `Priority = 0, PriorityMissing = true`.
   - Re-run `PlanFreshOnly` on the current quota cache and call `r.setDualSnapshot(dualSnap)`.
2. Remove the wrong frontend block: drop the local `changes.length === 0` check and let the backend do the strict diff and return the real write-back changes.

---

### 2.3 BUG-03: Config center form fails to show saved values due to i18n overrides and unsynced custom dropdowns

#### Root cause
1. In the HTML template, the custom dropdown trigger labels (e.g. `#customIntervalLabel`, `#customCfgModelLabel`) hard-coded `data-i18n="optInterval15m"` and `data-i18n="optGemini"`. Whenever the page loaded or `applyLanguage()` ran on a language switch, the label text was unconditionally overwritten back to the default.
2. When populating the form, `renderDynamicConfigForm` only updated the `value` of the hidden `<select>` and did not move the `.selected` highlight class on the `.custom-select-option` menu items.

#### Fix
1. Remove the hard-coded `data-i18n` attributes from the custom dropdown labels; `updateCustomIntervalDisplay()` and `updateCustomCfgModelDisplay()` handle i18n translation and label binding.
2. In the form-population and dropdown-change functions, iterate the `.custom-select-option` list so the `.selected` style stays strictly in sync with the current value.
3. On first page load, request `/config` asynchronously so the form is populated precisely once the response arrives.

---

### 2.4 BUG-04: Navbar "Refresh" button does not sync CPA host credential files

#### Root cause
The "Refresh" button at the top of the navbar only read `/snapshot/latest` from the plugin's local memory and cache, and never called the CPA host `ListAuthFiles` API. Credentials added or deleted in the host were invisible to the management UI.

#### Fix
1. The backend adds a core `Runtime.SyncHost` use case and a `POST /sync` management endpoint.
2. The top-bar "Refresh" button (`btnRefresh`) calls `POST /sync`, which pulls the latest credential file list from the CPA host, combines it with the local quota cache to build a fresh two-group snapshot, and returns it for rendering.

---

### 2.5 BUG-05: Credentials disabled on host lose quota fetching and countdown display

#### Root cause
In `initialItems` in `internal/priority/planner.go`, when `credential.Disabled == true` the code hit `continue` early and never extracted the credential's `PlanType`, `R5h`, `R7d`, or the reset countdowns of both windows. Manually disabled credentials therefore showed as `unknown` with every progress bar at 0.

#### Fix
1. In `initialItems`, still fully extract the `evidence` quota, real `PlanType`, and countdowns for credentials with `credential.Disabled == true`.
2. Keep `Disabled = true`, `Priority = -1`, and `Reason = "disabled on host"`, so the scheduler does not activate the credential while the UI still shows its real quota and reset times.
3. Complete the frontend i18n: `disabled on host` gets a Chinese translation meaning "manually disabled on host".

## 3. Feature Enhancements Detailed Spec

### 3.1 FEAT-01: Multi-dimensional adaptive scheduling score and adaptive bucketing

#### Problem
In the old single-dimension urgency model $\text{Urgency} = \frac{R_{\text{7d}}}{T_{\text{7d}}}$, the unit is `1/hour` and results typically fall between `0.001 ~ 0.015`. With the default `0.05` tolerance, every pair of normal active accounts (e.g. `rikacccccc` with 7% of 7d left and `owocccccc` with 73% left) differs by less than `0.05`, so all of them landed in the same bucket and got 100.

#### Composite score model
Introduce a composite score $S_{\text{composite}}$ combining four core dimensions:
$$S = w_1 \cdot P_{\text{weekly}} + w_2 \cdot R_{\text{7d}} + w_3 \cdot R_{\text{5h}} + w_4 \cdot A_{\text{5h}}$$

Where:
1. **Weekly relative burn pressure ($P_{\text{weekly}}$)**:
   $$P_{\text{weekly}} = \frac{R_{\text{7d}}}{\max(T_{\text{7d}}, 0.5) / 168.0}$$
   Normalized against 168 hours (7 days). $P_{\text{weekly}} > 1.0$ means there is more quota than remaining time needs, so it should be consumed faster; $P_{\text{weekly}} < 1.0$ means quota is being consumed too fast and needs protecting.
2. **Weekly absolute remaining ratio ($R_{\text{7d}}$)**: $R_{\text{7d}} \in [0.0, 1.0]$, so accounts with very little overall quota left are penalized significantly.
3. **5-hour short-window availability ($R_{\text{5h}}$)**: $R_{\text{5h}} \in [0.0, 1.0]$, so credentials with ample short-window quota take concurrent load first.
4. **5-hour short-window recovery acceleration ($A_{\text{5h}}$)**: $A_{\text{5h}} = 1.0 - \min\left(1.0, \frac{T_{\text{5h}}}{5.0}\right)$, so accounts whose short window is about to reset are consumed first.

*Default weights*: $w_1 = 0.40, w_2 = 0.30, w_3 = 0.20, w_4 = 0.10$.

#### Dynamic bucketing and stepped priority values
* Sort candidate accounts by composite score $S$ in descending order.
* Keep the `UrgencyTolerance` clustering: when adjacent credentials differ by $\Delta S \le \text{Tolerance}$, assign the same priority so the CPA host's native round-robin load balancing applies.
* When $\Delta S > \text{Tolerance}$, step down to the next bucket's priority, producing clear tiers (e.g. 100 -> 98 -> 92 -> 88 -> 65).

### 3.2 FEAT-02: Credential card dual display of actual and target/predicted priority, with status badges

#### Visual spec
The priority area at the bottom right of the credential card becomes a **primary/secondary dual display + status Tag**:

```
[Priority display spec]
+-------------------------------------------------------------------------+
| Actual: [100 / Unset / Disabled]  |  Target: [98]  [Pending write-back] |
| Reason: fresh remaining positive                                        |
+-------------------------------------------------------------------------+
```

1. **Actual Priority (`Actual Priority`)**:
   - Taken from `item.current.priority`.
   - If unset on the host (`PriorityMissing = true` or $\le 0$): show `[Unset]`.
   - If disabled on the host: show `[Disabled]`.
2. **Target/Predicted Priority (`Target/Predicted Priority`)**:
   - Taken from `item.target.priority`.
   - In the predicted view, show `Predicted: 98` with a `[🔮 Predicted]` badge.
   - In the control group, when the host's actual value differs from the target, add an amber `[Pending write-back]` status badge.

### 3.3 FEAT-03: Credential sample history view and drawer modal (QuotaSample visualization)

#### Feature and interaction design
1. **Card entry point**: a `📊 Samples` button on the right of the credential card's badge row.
2. **Sample drawer modal (`#samplesModal`)**:
   - The title shows the credential name and AuthIndex.
   - Calls `GET /samples?auth_index=xxx` asynchronously to fetch the credential's sample history for both the `gemini` and `claude_gpt` model groups in one go.

     - `#`: sample number
     - `Sampled at`: localized timestamp to the second
     - `5h remaining`: bold green percentage
     - `7d remaining`: bold blue percentage
3. **Empty state**: on a cold start with no consecutive probe samples yet, show a friendly empty state: *"No sample history yet (waiting for consecutive probes)"*.

### 3.4 FEAT-04: Apply confirmation merged with change preview (show the diff preview and confirm in one click)

#### Interaction flow
* **Clicking "Apply now" on the main screen**:
  1. No longer opens a bare Confirm dialog with no information.
  2. Opens a comparison modal listing the priority and disabled-state changes for every account to be updated (title: `⚡ Confirm priority write-back`).
  3. The modal footer has a `Confirm write-back` button.
  4. After the user clicks `Confirm write-back`, the write runs, the modal closes, a success Toast appears, and data refreshes; **no redundant result panel is shown**.
* **Dry-Run flow stays as is**:
  1. Clicking "Dry-Run" opens the full preview panel with detailed quota metrics and predicted values.
  2. The panel footer has an "Apply now" button that enters the write-back confirmation flow above.

### 3.5 FEAT-05: Countdown freezes when auto-schedule is paused, and every scheduler state is shown accurately

#### State machine and countdown behaviour
1. **Auto-schedule off (`AutoApply = false`)**:
   - Status badge: `⚪ Auto-schedule off`.
   - Top card & diagnostics: show `Scheduler status: Auto-schedule off`; the countdown stops.
2. **Manually paused (`Paused = true`)**:
   - Status badge: `⏸ Auto-schedule paused`.
   - Top card & diagnostics: show `Scheduler status: Auto-schedule paused`; the countdown freezes immediately and stops ticking.
3. **Sleeping outside the window (`Sleeping`)**:
   - Status badge: `🌙 Scheduler sleeping (outside run hours)`.
   - Top card & diagnostics: show `Scheduler status: Scheduler sleeping`; the countdown stops.
4. **Running normally (`Active`)**:
   - Status badge: `🟢 Auto-schedule running (09:00-23:00)`.
   - Top card & diagnostics: show the per-second adaptive countdown as usual (`Next run: 04m 20s`).

### 3.7 REFACTOR-01: Remove the redundant DryRun mechanism entirely

#### Motivation
* **Duplicated information in the UI**: the card list already shows "actual vs target/predicted priority" WYSIWYG, and "Apply now" already includes a pending-diff confirmation modal, so a separate "Dry-Run" button is a redundant entry point that crowds the control bar and adds mental load.
* **Split, ambiguous backend concepts**: the backend had `TriggerManual` (meaning dry run) and `TriggerManualApply` (meaning actual write-back), and `DryRun` was really just a thin wrapper around the `SyncHost` calculation plus one history entry, with no irreplaceable responsibility of its own.

#### Changes and code cleanup
1. **Simpler frontend**: remove `<button id="btnDryRun">` from the control bar and substantially simplify `showModal` (deleting 50+ lines of special-case code), so the modal focuses only on "write-back diff confirmation" and "run history details".
2. **Converged backend modes**: delete the `Runtime.DryRun` method, the `KindDryRun` constant, and the `TriggerManual` trigger; `handleRun` accepts only `mode=apply` and `mode=probe`.
3. **Clear semantics**: run triggers converge on three explicit actions: `TriggerManualApply` (manual write-back), `TriggerAutoApply` (scheduled automatic write-back), and `TriggerProbe` (manual quota probe).

---

### 3.8 FEAT-07: Fully visual System Diagnostics panel with 429 circuit-breaker monitoring

#### Motivation
* **The old screen just dumped raw JSON**: the System Diagnostics tab only had a one-line scheduler bar and a huge full-width `<pre>` block, with low information density and poor readability.
* **Dead field cleanup**: retire the `config_warnings` field, dead since the era of depending on CPA `config.yaml`.
* **No visibility into the core circuit breaker**: the state store already held 429 circuit-breaker records, but the diagnostics panel never showed them.

#### Design and implementation
1. **No more raw JSON dump**: remove the `<pre id="rawDiagnostics">` box and put a compact `📋 Copy diagnostics JSON` button in the top action bar.
2. **Three core KPI status cards across the top**:
   - Scheduler engine status (period, next-run countdown, running/paused/sleeping/off state badge).
   - 429 circuit-breaker monitor (green normal mark when healthy; when tripped, highlights the number of demoted, protected accounts).
   - Recent write health (success/failure/skip counts and the last write timestamp).
3. **Scheduler details and time-window board**: base parameters + all-day / time range and an active/sleeping indicator.
4. **429 circuit-breaker credential board (two states)**: with zero cooldowns, a clean green mark; with cooling credentials, a card list showing account, model group, trip reason, and a per-second recovery countdown.
5. **Recent write executions and redacted audit stream**: a one-line-per-entry redacted log board with colored status pills (Succeeded / Failed / Skipped / Attempted).

## 4. Architecture & Domain Model

### 4.1 Goals of the second round of architecture deepening

`v1.2.0` ships the second round's four architecture changes as one release scope: the Evidence module owns Fresh Evidence eligibility, the Dual Model Group Projection module owns the Control/Predicted views, the Planner stays a side-effect-free pure function, the Host Transition module commits and records the final Host result, and the Management page builds a single `StatusHTML` resource from assets organized by user feature.

All four changes follow implementation specs and tickets with blocking relationships published to the local issue tracker. Implementation advances along each change's frontier, and every ticket must stay independently verifiable; a change counts as done only after its last close-out ticket is complete.

## 5. Backend API & Protocol Evolutions

### 5.1 New API contracts

#### 1. `POST /v0/management/plugins/antigravity-priority/sync`
* **Purpose**: actively sync the credential file list from the CPA host and rebuild the two-group snapshot.
* **Parameters**: `?antigravity_model_group=gemini|claude_gpt` (optional).
* **Response**: `200 OK` with the full `DualGroupSnapshot` JSON.

#### 2. `GET /v0/management/plugins/antigravity-priority/samples`
* **Purpose**: get the sliding-window sample history for a given credential and model group.
* **Parameters**:
  * `auth_index` (required): credential identifier.
  * `antigravity_model_group` (optional, default `gemini`).
* **Response**:
  ```json
  {
    "auth_index": "auth_ag_001",
    "antigravity_model_group": "gemini",
    "samples": [
      {
        "observed_at": "2026-08-20T10:00:00Z",
        "short_window_reset_at": "2026-08-20T13:09:00Z",
        "short_window_rem": 95,
        "long_window_rem": 85
      }
    ]
  }
  ```

## 6. Frontend UX & State Machine

| Scenario | Trigger | System behaviour and state flow | What the user sees |
| :--- | :--- | :--- | :--- |
| **Host credential sync** | Click top-bar `Refresh` | Call `POST /sync` -> pull host files -> update snapshot | Toast "Synced the latest credential files from the CPA host"; cards refresh immediately |
| **Quota re-probe** | Click `Refresh quota` | Call `POST /run?mode=probe` -> probe Google API -> recompute two-group Plan | Button enters a 10s cooldown; cards refresh seamlessly and **never go blank** |
| **Reset priorities** | Click `Reset priorities` | Call `POST /reset` -> clear host field -> snapshot resets to PriorityMissing | Card shows `Actual: [Unset] | Target: 100 [Pending write-back]` |

| **Pause/resume scheduling** | Click the scheduler status badge | Toggle Paused state and save to backend | Countdown freezes immediately and shows `Paused`; resumes counting after Resume |
